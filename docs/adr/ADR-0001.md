# ADR-0001 — Build a deterministic offline core first

- **Status:** Accepted
- **Date:** 2026-10-15
- **Owner:** Project maintainer (review approval recorded by merging ADR proposal)
- **Scope:** M0

## Context

The main uncertainty is correct Unicode identification, not UI construction. Starting with a browser adapter would conflate detection defects with browser lifecycle defects.

## Decision

Build a synchronous, pure TypeScript analyzeDomain operation. Accept a hostname and explicitly injected catalog/versioned datasets. Do not require a network, database, browser API, account, or AI service. Wrap it in a browser adapter only after M0 verification.

## Alternatives considered

Build UI and core concurrently (faster demo but hides algorithmic issues); backend reputation API (privacy and operational scope); general-purpose security SDK (opaque behavior and unwanted abstractions).

## Consequences

Portable, deterministic, auditable and testable. User-facing browser warnings must wait for M1.

## Evidence required for acceptance

Identical inputs and pinned datasets reproduce identical results; tests and dependency inspection show no runtime network calls.

## Acceptance scope and remaining implementation evidence

**Design acceptance does not certify implementation.** This decision approves the architectural boundary: implement and verify a synchronous, pure, deterministic TypeScript core before any browser adapter or network integration. The existing Gate 0 IDNA/PSL behavior and source-provenance probes inform the design but are **not** proof that `analyzeDomain()` exists.

M0 verification still must prove identical outputs for identical hostname, injected catalog and fixed data versions; no runtime network/browser/AI imports; bounded parsing and stable results. This ADR does not authorize M0-01 by itself, and it does not approve distribution or a Chrome extension.

## Decision gate

**Design policy accepted by the maintainer through the reviewed ADR PR merge.** Gate 0 closure and the explicit internal M0-01 start decision are separately required; actual implementation verification is deferred to the relevant M0 gate.
